1. 概述与对接流程

开放平台提供客户建档、表单结构查询、表单数据提交与编辑、以及健康日志（血糖 / 饮食 / 血压 / 体重）查询能力，共 8 个接口。第三方可以查询项目下的表单定义，以客户为单位提交 / 修改表单数据，也可以按客户查询历史提交的健康日志记录。

1.1 核心概念

概念说明
公司（company）开放平台的接入主体。每个接入方对应平台内一家公司，凭证（app_key / app_secret）按公司发放
项目（project）公司下的业务项目，编码为 project_code。一家公司可有多个项目，所有业务接口都要求传 project_code，且该项目必须属于当前 app_key 所属公司，否则 40301
表单（form）项目下的一张数据采集表单，编码为 form_code，由若干字段组成
字段（field）表单的最小数据单元，编码为 field_code，有类型（文本 / 单选 / 日期…）与校验规则
客户（owner）数据的归属人。第三方不接触平台内部客户编码，通过手机号、微信 UnionID 或 customer_code 指代客户，由平台在项目内映射到具体客户。客户须先建档（见 5.1）
提交（submission）/ 日志（log）同一份数据的两种称呼：5.4 新增表单提交 写入的记录，审核通过后可通过 5.7 查询日志列表 查到（仅限血糖 / 饮食 / 血压 / 体重四类表单）

1.2 对接流程

① 线下申请接入 ──► 平台发放 app_key / app_secret，并告知 project_code
② 调用 5.1 客户建档 ──► 记录返回的 customer_code（幂等，客户已存在则返回既有的）
③ 调用 5.2 查询表单列表 ──► 拿到项目下可用的 form_code
④ 调用 5.3 查询表单结构 ──► 拿到字段清单、类型、校验规则（建议缓存）
⑤ 按第 4 节数据字典组装 field_values ──► 调用 5.4 新增提交，记录返回的 submission_code
⑥ 数据有误需修正 ──► 调用 5.5 编辑提交
⑦ 联调回查 ──► 调用 5.6 查询提交详情
⑧ 需要按客户批量回看历史健康日志（仅限血糖/饮食/血压/体重四类，且需已审核）
   ──► 调用 5.7 查询日志列表 / 5.8 查询日志详情

② 是先决条件：表单数据必须挂在一个已建档的客户上。客户若已由平台侧录入，这一步可跳过，或照样调用一次拿 customer_code（幂等，不会建重复）。③④ 是可选步骤：如果已经知道要用的 form_code，可以直接从 ⑤ 或 ⑧ 开始。

2. 通用约定

2.1 环境地址

接口按用途分布在两个地址下，调用前请对照下表确认发往哪个地址：

环境Base URL
测试环境https://open-api-test.deepaihealth.cn
生产环境https://open-api.deepaihealth.cn

所有接口路径以 /v1/ 开头，下文接口路径均为相对 Base URL 的路径。

2.2 协议约定

  • 统一使用 HTTPS + POST + JSON（Content-Type: application/json; charset=utf-8）
  • 字符编码统一 UTF-8
  • 时间统一使用北京时间（UTC+8），格式 YYYY-MM-DD HH:mm:ss（日期为 YYYY-MM-DD）
  • 请求体大小上限 2 MB
  • 所有参数一律放请求体，接口不接受 query 参数；携带 query 的请求直接返回 40001

2.3 公共请求头

Header必填说明
Content-Type✓application/json; charset=utf-8
X-App-Key✓平台发放的应用标识
X-Timestamp✓毫秒级时间戳，与服务器时间偏差不得超过 ±5 分钟
X-Nonce✓随机字符串（16~64 位，建议 UUID），10 分钟内不得重复，用于防重放
X-Sign✓请求签名，算法见第 3 节
X-Sign-Version—签名协议版本，当前为 2。可不传；传了则必须为 2，否则返回 40001。建议显式传，便于后续协议升级平滑过渡

2.4 统一响应格式

所有接口（含业务失败）均返回 HTTP 200，以响应体中的 code 判断结果：

// 成功
{
  "code": 0,
  "msg": "OK",
  "data": { /* 业务数据，无数据时为 null */ },
  "request_id": "b3bee3093be34976863cdcb3733fa030"   // 每次请求唯一，排查问题时请提供
}

// 失败
{
  "code": 42201,
  "msg": "字段校验失败",
  "data": { /* 部分错误码会携带明细，见各接口说明 */ },
  "request_id": "..."
}

仅当网关层异常（路径不存在、服务不可用）时才会出现非 200 的 HTTP 状态码，此时响应体不保证为上述格式。

2.5 限流

  • 按 app_key 限流，默认 300 次/分钟（如需更高配额请联系平台）
  • 限流按 2.1 表中的地址分别计数：打到 open-api 地址的请求和打到 open-query-api 地址的请求配额互不影响
  • 超限返回 code = 42901，响应头携带：
响应头说明
X-RateLimit-Limit当前窗口配额
X-RateLimit-Remaining当前窗口剩余次数
X-RateLimit-Reset窗口重置时间（秒级时间戳）

2.6 幂等性

  • 客户建档（5.1） 幂等：同一 project_code + owner 重复调用只返回既有客户，不会重复建档
  • 新增提交（5.4） 支持幂等：请求中可传第三方业务单号 external_no（项目内唯一）。同一 project_code + external_no 重复调用不会产生重复数据，返回首次创建的结果，并以 data.is_duplicate = true 标识
  • 编辑提交（5.5） 天然幂等：同一请求重复调用结果一致
  • 网络超时等异常场景，建议使用 external_no + 重试（建议指数退避，最多 3 次）

查询类接口（5.2、5.3、5.6、5.7、5.8）本身不涉及写入，不需要考虑幂等。

2.7 日志查询范围与排序约定

  • form/list、form/detail 可查 project_code 对应项目下任意启用中的表单结构，不限于血糖 / 饮食 / 血压 / 体重
  • log/find、log/find_detail 只接受 form_code 四选一，且只返回 submission_status = 2（已审核）的记录 —— 草稿、待审核、已驳回、已删除的记录一律查不到
  • log/find 固定按 submit_time 倒序（最新的在前），不支持自定义排序方向；分页用 page / page_size，默认第 1 页、每页 20 条，最大 100 条
  • 查询永远限定在 owner 解析出的那一个客户名下，不支持跨客户批量查询

3. 签名机制

3.1 凭证

凭证说明
app_key应用标识，随请求头明文传输
app_secret签名密钥，仅保存在第三方服务端，严禁写入前端 / App / 小程序等客户端，严禁随请求传输

如怀疑 app_secret 泄露，请立即联系平台重置。

3.2 签名算法（HMAC-SHA256）

stringToSign = METHOD + "\n" + PATH + "\n" + X-Timestamp + "\n" + X-Nonce + "\n" + requestBody
X-Sign = lowercase( hex( HMAC-SHA256( app_secret, stringToSign ) ) )

要点：

  1. METHOD 为大写请求方法。本文档所有接口均为 POST
  2. PATH 为不含 query 的请求路径，以 / 开头，如 /v1/form/detail。按实际发送的字面值参与签名，服务端不做归一化——大小写、结尾斜杠都敏感，两端必须完全一致
  3. requestBody 为实际发送的原始 JSON 字节串（UTF-8）。计算签名与发送请求必须使用同一份序列化结果，不要序列化两次（键顺序、空格差异都会导致验签失败）
  4. 五段之间用换行符 \n（LF，0x0A）连接，末尾没有换行符
  5. 结果为 64 位小写十六进制字符串
  6. 服务端校验顺序：app_key → 限流 → 时间戳窗口（±5 分钟）→ nonce 是否重复 → 签名比对，任一不通过分别返回 40101/40102 / 42901 / 40104 / 40105 / 40103

方法与路径纳入签名，是为了让一次签名只对它本来要访问的那个接口有效，无法被中间环节改道到其它接口。签名不含域名，请确保请求实际发送的地址与 2.1 表中一致，发错地址会直接连接失败或 404，与签名无关。

3.3 计算示例

给定：

app_key    = ak_demo_7f3a9c2e1b6d
app_secret = sk_demo_2b8f4a6c9e1d3f5a7b0c
method     = POST
path       = /v1/log/find
timestamp  = 1789267200000
nonce      = 8e4a1c6f9b3d2a7e
body       = {"project_code":"proj_demo_0001","form_code":"form_blood_glucose_log","owner":{"type":"phone","value":"13800138000"},"page":1,"page_size":20}

则：

stringToSign =
POST\n/v1/log/find\n1789267200000\n8e4a1c6f9b3d2a7e\n{"project_code":"proj_demo_0001","form_code":"form_blood_glucose_log","owner":{"type":"phone","value":"13800138000"},"page":1,"page_size":20}

X-Sign = fb9bec6f23c67846da1fa961cea4076b8ed4b671ac0c6b54f106237c81293c58

请先用本组数据验证你的签名实现，再进行联调。完整 curl 与多语言示例代码见附录。

  { "name": "检查报告-2.jpg", "url": "https://example.com/reports/2.jpg" }

value_type说明

Float浮点数

4.3 校验规则与选项

以下内容只有 form/detail（5.3）才返回（log/find、log/find_detail 只返回字段的值，不返回结构定义）：

"validation_rules": [
  { "required": true, "message": "请输入空腹血糖值" }
],
"options": [
  { "label": "空腹", "value": "fasting" }        // Select/Radio/Checkbox/Cascader 才有；Cascader 的 children 层级不限
],
"switch_values": { "checked_value": 1, "unchecked_value": 0 }   // 仅 Switch 才有

required 已经把字段级与关系级的必填规则汇总好了，可以直接用字段的 required 属性，不必自己再解析 validation_rules 数组。提交值必须取自 options[].value（Cascader 取一条完整路径上各级的 value）。

4.4 日志查询接口的字段值还原规则

表单数据在主平台按「一行一个字段」的方式落库，field_value 原始存的是字符串。log/find（5.7）、log/find_detail（5.8）在返回前会按字段的 field_type / value_type 把它还原成下表对应的 JS/JSON 类型，第三方拿到的就是可以直接用的值，不需要再自己解析（submission/detail（5.6）不做这层还原，按其自身响应示例的口径为准）：

落库存的是还原规则还原后
Checkbox / Cascader / UploadImage / UploadFile 的值JSON.parse数组
Select，multiple=trueJSON.parse数组
Select，单选原样返回字符串
Switch转数字，失败则原样返回number（或字符串兜底）
Input，value_type 为 Integer/Float转数字，失败则原样返回number（或字符串兜底）
其它（Textarea/Date/DateTime/字符串型 Input 等）原样返回字符串

5. 接口详情

以下接口的请求体均为业务参数；签名相关参数一律放请求头（见 2.3），不进请求体。每个接口卡片右侧标注了实际调用地址（对照 2.1）。

5.1 客户建档

在项目内为客户建档，使其可以作为 5.4 的 owner 使用。本接口幂等：同一标识重复调用不会重复建档，只会把已有客户原样返回。

POST/v1/customer/createopen-api

请求参数

字段类型必填说明
project_codestring(80)✓项目编码
ownerobject✓客户标识。建档用什么标识，之后提交就能用什么标识
owner.typestring✓phone（手机号）或 wechat_unionid（微信 UnionID）。此处不接受 customer_code——它是建档的产物，不是入参
owner.valuestring(64)✓标识值
customer_namestring(50)✓客户姓名，平台客户列表直接展示该字段
genderint—0-未知（默认）/ 1-男 / 2-女

响应 data

{
  "customer_code": "cust_7b2e1d9a4c6f8e0b3d5a7c9e1f2b4d6a",  // 平台客户编码，建议存入自己系统
  "owner": { "type": "phone", "value": "13800138000" },
  "existed": false                                          // true 表示该标识此前已有建档，本次未新建
}

建议把 customer_code 存进自己的系统：后续 5.4 提交时用 owner: {"type": "customer_code", "value": "cust_…"} 是最稳的一种指代方式 —— 它在项目内唯一，不受客户换手机号影响，也不会撞上 40404。

幂等说明：以 project_code + owner 为准。已有该标识的启用建档时返回 existed: true 与既有 customer_code，不会新建、不会覆盖已有客户资料。并发重复调用同样只会建出一条。

错误：项目不属于当前凭证 → 40301；该标识已有建档但被禁用 → 40405（禁用通常是平台侧有意为之，接口不会绕过它另建一条）；该标识已对应多条启用建档 → 40404。

建档只写入姓名、性别与本次使用的那一个标识。若同一客户既有手机号又有 UnionID，需要两个标识都挂在同一条建档上，请联系平台在后台补录 —— 分两次调用本接口会建出两条独立客户。

5.2 查询表单列表

获取项目下可用的表单。不限于血糖 / 饮食 / 血压 / 体重 —— 项目下有多少启用中的表单，就能查到多少（实测某测试项目下有 21 个）。

POST/v1/form/listopen-api / open-query-api

请求参数

字段类型必填说明
project_codestring(80)✓项目编码，必须属于当前 app_key 所属公司
pageint—页码，默认 1
page_sizeint—每页条数，默认 20，最大 100

响应 data

{
  "total": 35,
  "page": 1,
  "page_size": 20,
  "list": [
    {
      "form_code": "form_demo_body_index",
      "form_name": "身体指标记录表",
      "form_description": "记录客户体重、血压等基础指标",
      "updated_at": "2026-06-01 10:00:00"     // 表单定义最后更新时间，可用于判断本地缓存是否失效
    }
  ]
}

错误：项目不属于当前凭证所属公司 → 40301。

仅返回启用中的表单；禁用表单不下发，也不接受提交。

5.3 查询表单结构

获取表单的字段清单与校验规则。建议缓存（按 5.2 的 updated_at 判断失效），不要每次提交前实时拉取。

8. 对接注意事项与 FAQ

  1. 接口分布在两个地址下，为什么要分开排查限流？ 限流按 2.1 表中的地址分别计数（各自独立的 Redis 状态），凭证共用不代表配额共用。排查 42901 时先确认调用的是哪个地址
  2. 能不能只用日志查询相关接口，不用提交类接口？ 可以，如果只需要读取平台内已有的健康日志。反过来只用提交类接口也可以，只是拿不到 5.7/5.8 的批量日志查询能力（submission/detail 可以按单号回查自己写过的数据，但不支持按 owner 批量查历史）
  3. 为什么写完 submission/create 之后立刻用 log/find 查不到？ log/find、log/find_detail 只返回 submission_status = 2（已审核）的记录，新提交的数据要先经过平台侧审核流程
  4. 为什么只能查血糖 / 饮食 / 血压 / 体重这四类日志？ 这是 log/find、log/find_detail 当前的开放范围。项目下还有运动日志、营养档案等其它表单，可以用 form/list、form/detail 查到结构，但日志查询目前只对这四类开放
  5. 为什么每次都要传 project_code，还要保证归属正确？ 一把 app_key/app_secret 凭证可能对应一家公司名下的多个项目。每个接口都会校验 project_code 是否属于当前凭证所属公司，不属于直接 40301
  6. 为什么查详情传错 owner 返回"记录不存在"（40402），而不是"无权限"？（log/find_detail）故意如此设计，避免告诉调用方"这个 submission_code 确实存在"，防止被用来批量探测别人的记录
  7. 客户怎么标识？ 建档（5.1）时只接受 phone / wechat_unionid；建档之后的提交 / 查询接口，owner.type 可以是 phone、wechat_unionid 或 customer_code 三选一。推荐 customer_code——项目内唯一，结构上不可能出现 40404
  8. 能查到未审核 / 草稿状态的记录吗？ 不能，log/find、log/find_detail 只返回已审核记录
  9. 列表能按时间范围筛选、能改排序方向吗？ 首期都不支持，form/list 与 log/find 均只支持 page / page_size 分页；log/find 额外固定按提交时间倒序
  10. 能删除提交吗？ 首期不开放删除。误提交请联系平台处理
  11. 上传类字段的文件放哪里？ 首期由第三方提供公网可访问的 HTTPS 直链，平台不代存
  12. 表单结构会变吗？ 会。建议缓存 + 按 updated_at 失效重拉；收到 42201 且 reason 指向未知字段时主动刷新缓存
  13. 重试怎么做才安全？ submission/create 一律带 external_no；超时后重试同一请求（同 external_no + 新 nonce + 新 timestamp + 重新签名）。nonce 不能复用，签名要重算
  14. 测试环境有沙箱数据吗？ 平台会在测试环境为接入方准备演示项目（含示例表单与测试客户），随凭证一并提供

const crypto = require('crypto');

// apiPath 为不含 query 的接口路径，如 '/v1/log/find' 或 '/v1/customer/create'
function buildHeaders(appKey, appSecret, apiPath, bodyObj) {
  const body = JSON.stringify(bodyObj);           // 发送时必须复用这份序列化结果
  const timestamp = Date.now().toString();
  const nonce = crypto.randomUUID().replace(/-/g, '');
  const stringToSign = `POST\n${apiPath}\n${timestamp}\n${nonce}\n${body}`;
  const sign = crypto.createHmac('sha256', appSecret).update(stringToSign, 'utf8').digest('hex');
  return {
    body,
    headers: {
      'Content-Type': 'application/json; charset=utf-8',
      'X-App-Key': appKey,
      'X-Timestamp': timestamp,
      'X-Nonce': nonce,
      'X-Sign-Version': '2',
      'X-Sign': sign,
    },
  };
}

import hashlib
import hmac
import json
import time
import uuid


# api_path 为不含 query 的接口路径，如 "/v1/log/find" 或 "/v1/customer/create"
def build_headers(app_key: str, app_secret: str, api_path: str, body_obj: dict):
    body = json.dumps(body_obj, ensure_ascii=False, separators=(",", ":"))  # 发送时必须复用这份序列化结果
    timestamp = str(int(time.time() * 1000))
    nonce = uuid.uuid4().hex
    string_to_sign = f"POST\n{api_path}\n{timestamp}\n{nonce}\n{body}"
    sign = hmac.new(app_secret.encode("utf-8"), string_to_sign.encode("utf-8"), hashlib.sha256).hexdigest()
    headers = {
        "Content-Type": "application/json; charset=utf-8",
        "X-App-Key": app_key,
        "X-Timestamp": timestamp,
        "X-Nonce": nonce,
        "X-Sign-Version": "2",
        "X-Sign": sign,
    }
    return body, headers

import javax.crypto.Mac;
import javax.crypto.spec.SecretKeySpec;
import java.nio.charset.StandardCharsets;
import java.util.UUID;

public final class OpenApiSigner {

    /** path 为不含 query 的接口路径，如 /v1/log/find 或 /v1/customer/create */
    public static String sign(String appSecret, String method, String path,
                              String timestamp, String nonce, String body) throws Exception {
        String stringToSign = method + "\n" + path + "\n" + timestamp + "\n" + nonce + "\n" + body;
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(appSecret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
        byte[] digest = mac.doFinal(stringToSign.getBytes(StandardCharsets.UTF_8));
        StringBuilder hex = new StringBuilder();
        for (byte b : digest) {
            hex.append(String.format("%02x", b));
        }
        return hex.toString();
    }

9.5 签名自测清单

联调前请依次确认：

  • 用 3.3 示例数据算出的签名 = fb9bec6f23c67846da1fa961cea4076b8ed4b671ac0c6b54f106237c81293c58
  • 签名串共 5 段：方法、路径、时间戳、随机串、请求体，顺序不能错
  • 参与签名的路径与实际请求的路径完全一致（含大小写与结尾斜杠），且不带 query
  • 参与签名的 body 与实际发送的 body 是同一份字节串（同一次序列化）
  • 时间戳为毫秒级、服务器时间已做 NTP 校准
  • 每次请求（含重试）都生成新 nonce 并重新签名
  • 请求实际发送的地址与 2.1 表一致——发错地址会连接失败或 404
  • project_code 已确认属于当前凭证所属公司，避免联调时反复碰到 40301
  • app_secret 只存在于服务端配置，未出现在任何客户端代码 / 日志 / 版本库中
